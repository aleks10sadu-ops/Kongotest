# Доставка и самовывоз с выбором даты и времени

Дата: 2026-08-24

## Цель

Добавить в существующее оформление заказа два способа получения — доставку и самовывоз — и разрешить для обоих способов либо заказ «как можно быстрее», либо заказ к выбранной дате и времени. Сохранить текущие интеграции iiko, Telegram, стоп-листа, бизнес-ланчей, минимальной суммы и журнала попыток.

## Согласованные правила

- Самовывоз доступен от 1 000 ₽ либо при заказе минимум двух бизнес-ланчей.
- Для доставки сохраняются действующие минимумы по зоне. Для бесплатной зоны действует минимум 1 000 ₽ либо два бизнес-ланча.
- Доставка и самовывоз используют единое расписание: Пн–Чт 12:00–21:45, Пт–Сб 12:00–23:00, Вс 13:00–21:45, часовой пояс Europe/Moscow.
- Для обоих способов остаётся вариант «Как можно быстрее».
- Отложенный заказ выбирается через календарь и список времени с шагом 15 минут.
- Прошедшие даты и время вне рабочего расписания недоступны.
- Запреты бронирования на 1 сентября, период декабря/января и ограничения из `reservation_settings` к заказам еды не применяются.
- Адрес самовывоза: Дмитров, Промышленная улица, 20Б.

## Не входит в задачу

- Онлайн-оплата и изменение существующих способов оплаты.
- Несколько точек самовывоза.
- Изменение меню, цен, зон доставки или расписания ресторана.
- Изменение правил бронирования столов.
- Новый канал Telegram или новая таблица Supabase.

## Интерфейс

`app/menu/DeliveryCheckout.tsx` остаётся единственной точкой оформления заказа. В верхней части формы появляется переключатель `Доставка / Самовывоз`. По умолчанию выбрана доставка, поэтому открытая старая корзина и привычный сценарий сохраняют текущее поведение.

Общие поля для обоих способов:

- имя и телефон;
- «Как можно быстрее / К дате и времени»;
- способ оплаты и сумма для сдачи;
- комментарий, аллергии и согласие на обработку данных;
- состав корзины и итоговая сумма.

Только для доставки показываются карта, улица, дом, детали адреса, найденная зона и стоимость доставки. Только для самовывоза показывается статичный адрес ресторана. Стоимость доставки для самовывоза равна нулю.

Успешный экран и кнопка отправки используют выбранный способ: «Заказать доставку» либо «Заказать самовывоз», «Заявка на доставку принята» либо «Заявка на самовывоз принята».

## Селектор даты и времени

Переиспользуется `app/components/DateTimePicker.tsx`. В компонент добавляется явный флаг, отключающий загрузку ограничений бронирования. Значение по умолчанию сохраняет текущее поведение бронирования; чекаут передаёт отключённый режим.

Для заказа используется полный режим даты и времени:

- календарь запрещает прошлые даты;
- список времени строится с шагом 15 минут по расписанию выбранного дня;
- для сегодняшней даты скрываются уже прошедшие слоты;
- конечное время рабочего окна разрешено как время готовности заказа;
- смена даты сбрасывает ранее выбранное время, если оно недоступно в новом дне.

Клиентские ограничения служат удобству, но не считаются защитой: сервер повторяет всю проверку.

## Модель запроса и обратная совместимость

В запрос `/api/orders` добавляется поле:

```ts
fulfillmentType: 'delivery' | 'pickup'
```

Существующие поля времени сохраняются, чтобы не ломать Telegram fallback и старые открытые вкладки:

```ts
deliveryTime: 'asap' | 'custom'
deliveryTimeCustom?: string // локальное время ресторана YYYY-MM-DDTHH:mm:ss
```

Если `fulfillmentType` отсутствует, сервер считает заказ доставкой. Поле `type: 'delivery'` в Telegram payload остаётся общим типом заказа еды; способ получения различается через `fulfillmentType`.

## Серверные правила времени

Чистые функции расписания в `lib/delivery/schedule.ts` расширяются так, чтобы проверять не только текущее открытие, но и выбранную локальную дату/время ресторана.

Для `asap` сервер требует, чтобы ресторан был открыт в момент запроса. Для `custom` сервер требует:

- корректный локальный формат даты и времени;
- момент не в прошлом по Europe/Moscow;
- попадание времени в окно выбранного дня.

Отложенный заказ разрешено отправлять вне текущего рабочего времени, если выбранное время валидно. Для дат заказа не вводится произвольный лимит по месяцам и не применяются календарные запреты бронирования.

Если в корзине есть бизнес-ланч, окно Пн–Пт 12:00–16:00 проверяется по выбранному времени выполнения отложенного заказа. Для `asap` сохраняется проверка по текущему московскому времени.

## Минимальный заказ и адрес

Для доставки сервер продолжает определять зону по координатам или `zoneName` и применяет `validateMinOrder` с этой зоной.

Для самовывоза сервер вызывает то же правило без платной зоны: минимум 1 000 ₽ или два бизнес-ланча. Адрес, координаты и зона не обязательны и не используются. В журнал заказа вместо адреса записывается «Самовывоз: Дмитров, Промышленная улица, 20Б».

Стоп-лист, очистка несовместимого гарнира и обязательный `productId` применяются одинаково для обоих способов.

## iiko

Аргументы создания заказа в `lib/iiko/orders.ts` получают `fulfillmentType`; адрес становится обязательным только для доставки.

- доставка: `orderServiceType: 'DeliveryByCourier'`, `deliveryPoint` передаётся как сейчас;
- самовывоз: `orderServiceType: 'DeliveryByClient'`, `deliveryPoint` не передаётся;
- выбранное время для обоих способов уходит в `completeBefore` в локальном формате iiko;
- `sourceKey: 'Сайт'`, телефон, клиент, комментарий, позиции и опрос результата создания сохраняются.

Сборка тела iiko выделяется в чистую функцию. Это позволяет проверить точное различие payload без сетевого запроса и без мокирования поведения iiko.

## Telegram

Основной путь остаётся прежним: успешный заказ создаётся в iiko, затем `supabase/functions/iiko-webhook/index.ts` отправляет сообщение в существующую группу и атомарно фиксирует его в `iiko_notified_orders`. Поллер остаётся страховкой вебхука и продолжает редактировать то же сообщение при смене статуса.

Форматирование основного и резервного сообщений различает способ получения:

- `🚚 Новая доставка` с адресом;
- `🛍 Новый самовывоз` без адреса, с адресом точки получения;
- для обоих показываются выбранные дата/время, клиент, позиции, сумма и комментарий.

`app/api/telegram/route.ts` принимает `fulfillmentType` для fallback-сообщения. Отсутствующее поле трактуется как доставка, чтобы старый payload не изменил смысл.

Основная карточка заказа всегда приходит сразу, в том числе для будущей даты. Меняется только отдельное напоминание «заказ не подтверждён»: оно отправляется в момент `max(семь минут после основной карточки, открытие ресторана в дату исполнения)`. Открытие считается по Москве: 12:00 с понедельника по субботу и 13:00 в воскресенье. Для заказа, созданного уже после открытия в дату исполнения, сохраняется обычная задержка семь минут. Дедупликация, `tg_message_id`, `orig_text`, счётчик напоминания и громкие сообщения об отмене сохраняются.

## Ошибки и безопасность

- Осознанные серверные отказы по расписанию, стоп-листу, бизнес-ланчу, минимальной сумме и неверной дате не должны уходить в Telegram fallback.
- В fallback уходит только технический сбой создания iiko, как и сейчас; сообщение явно требует пробить заказ вручную.
- Сервер не доверяет клиентской стоимости доставки, типу получения, дате или зоне и пересчитывает применимые правила.
- Неизвестный `fulfillmentType` отклоняется ответом 400.
- Ошибка Telegram после успешного создания iiko не создаёт второй заказ; её страхует существующий поллер.

## Критерии готовности

- Пользователь может оформить доставку или самовывоз как можно быстрее.
- Пользователь может оформить оба способа на будущую допустимую дату и 15-минутный слот.
- Запреты бронирования не блокируют даты заказа еды.
- Сервер отклоняет подменённые или устаревшие payload до обращения к iiko.
- iiko получает правильный `orderServiceType`, время и наличие/отсутствие адреса.
- В Telegram сразу приходит ровно одно основное сообщение с правильным способом получения; повторный алерт о неподтверждённом будущем заказе не приходит раньше открытия в дату доставки или самовывоза.
- Старый сценарий доставки и открытые до деплоя вкладки продолжают работать как доставка.
